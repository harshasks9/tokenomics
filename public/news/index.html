00 / Executive Summary

One page for the people who read one page

MERIDIAN is a Google Cloud–native agentic system that converts AI news into intelligence a leader can act on before their first meeting. It is built around one promise and one anti-pattern.

The promise

Every published item passes the leadership test: would a GTM leader, PM, or MD change a decision, a talk track, a deal strategy, or a watchlist because of this? If not, it is filtered out. The system reasons against a living portfolio taxonomy (Gemini, Vertex AI, Gemini Enterprise, Agentspace, AI infrastructure, security, data, GTM motions) and a named-competitor set (Microsoft, OpenAI, AWS, Anthropic, Meta, NVIDIA, Databricks, Snowflake + adjacents).

The anti-pattern it refuses

Generic AI-news summarization. MERIDIAN never blends fact and inference in one sentence; every factual claim carries a source and date, every inference carries a confidence (high/medium/low). Recommendations are concrete and role-addressed — "Field enablement: refresh the Copilot TCO battlecard in 5 business days" — never "monitor the situation."

What it produces

Daily log

8-field items, fact/inference separated, mapped to portfolio + competitors, with recommended actions. Published 09:00 SGT.

Drilldown

Double-click any item → fact pattern, offering linkage, and a verdict: Opportunity / Risk / Urgent / No-action, with confidence.

Synthesis

Weekly→yearly roll-ups that surface themes, path dependency, and market direction — not chronological recaps.

Memory

An assumption ledger that grades its own predictions, and a theme registry with promotion rules from weak signal → trend.

Decisive stance on the central trade-off. Recall vs. precision: MERIDIAN optimizes for precision at the daily layer (a leader's attention is the scarcest resource) and pushes recall into a searchable corpus + borderline queue. A missed minor item resurfaces in weekly synthesis; a false-positive daily item erodes trust permanently. We protect trust.

Build posture

Google Cloud–native: Cloud Run jobs + Workflows for orchestration, Cloud Scheduler for the 09:00 SGT anchor, Vertex AI (Gemini) for extraction/analysis/synthesis, BigQuery as the event + memory warehouse, Pub/Sub for stage hand-off, Vertex Vector Search for dedupe/RAG. An MVP (daily log + weekly synthesis + one visualization + basic drilldown) is achievable by a small team in 4–6 weeks.

Consumption principle

Same corpus, different lenses. Persona = a saved filter over portfolio areas, regions, and impact vectors + a default cadence — not a separate data pipeline.

Altitude principle

Daily items are tactical; synthesis is strategic. The MD and CoS live in synthesis; the PM and SE lead live in daily + drilldown.

Trust principle

Every persona sees the same fact/inference separation and citations. Trust is portable across altitudes; a leader can always click down to the primary source.

Paywalled sources

Prefer licensed API access (Bloomberg/Reuters/The Information). Where only headlines are legally available, MERIDIAN ingests metadata + abstract for scoring and links out — it never republishes licensed full text. Access + license tier is stored per source for governance.

Ingestion mechanics

A Cloud Run ingest job per tier writes raw payloads to raw_article (GCS + BigQuery) with fetch timestamp, source id, and license tier. Robots/ToS honored; crawl-delay respected; a source-health monitor flags feeds that go stale > 2 cycles.

Coverage over any single source. No item reaches "confirmed" on one source alone (see §4). The source list is a living config in BigQuery, versioned — adding a source is a data change, not a code deploy.
03 / News Relevance Scoring Methodology

A numeric gate that kills generic AI headlines

Every candidate story gets a 0–100 relevance score from seven weighted dimensions, computed by a constrained Gemini Flash call that returns JSON with per-dimension evidence. The design intent: a "cool new AI demo" with no portfolio proximity and no competitor materiality cannot clear the bar, no matter how viral.

DimensionWeight0Scoring anchor (10)
Impact-vector strength22%No plausible impact vector.Clearly moves ≥2 of the 8 vectors (strategic/commercial/product/competitive/regulatory/ecosystem/buying/capital).
Portfolio proximity20%Unrelated to Google Cloud AI.Directly names/affects a core offering (Gemini, Vertex, Agentspace, TPU…).
Competitor materiality18%No named competitor involved.Priority competitor (MSFT/OpenAI/AWS/Anthropic) makes a strategic move.
Magnitude / blast radius14%Niche, one customer.Reshapes a market, pricing tier, or standard.
Novelty10%Rehash of known info.Genuinely new fact / first disclosure.
Source authority9%Anonymous / T4 only.T1 primary or multiple T2 corroboration.
Time sensitivity7%Evergreen.Decision window closing in days (event, deadline, live deal).

Threshold: ≥ 62

Publishes to the daily log. A hard portfolio-or-competitor gate also applies: any item scoring <3/10 on both portfolio proximity and competitor materiality is auto-excluded regardless of total — this is what kills generic AI headlines.

Borderline queue: 50–61

Held for lightweight human triage (CoS/analyst) with a one-click include/exclude. Feeds the golden set (§12). Anything an editor promotes is logged as a training signal.

Below 50

Dropped from the daily log but retained in the corpus + embeddings, so it can still surface in weekly pattern detection or Q&A retrieval.

04 / Deduplication & Source Credibility

One story, many mouths — collapse it, then corroborate it

The same event arrives from dozens of outlets within minutes. MERIDIAN clusters near-duplicates by embedding similarity into a single canonical event, then applies corroboration rules before that event may claim "confirmed" status.

Same-story clustering

Each article is embedded (Vertex text-embedding). New articles are matched against the last 72 h of canonical events via Vector Search. Cosine ≥ 0.86 + shared primary entity + within a 36 h window → attach to the existing cluster; otherwise open a new canonical event. Clustering is re-checked after entity extraction to catch paraphrase-heavy rewrites.

Canonical-story selection

Within a cluster, the canonical source is chosen by: (1) primary/T1 > T2 > others; (2) earliest timestamp among equal tiers; (3) most complete fact pattern. All member articles are retained as corroboration and for citation diversity.

Credibility tiers & status ladder

StatusRequirementHow it's shown
ConfirmedT1 primary source, OR ≥2 independent T2+ sources agreeing on the core fact.Fact block, no hedge; source list shown.
ReportedSingle credible T2 source, not yet corroborated.Fact block tagged "reported by X, awaiting corroboration."
Rumor / unverifiedT4 signal, anonymous sourcing, or leak.Held out of the fact block; appears only in inference with low confidence and a "rumor" flag.
DisputedCredible sources conflict on the core fact.Both accounts shown; verdict withheld pending resolution; flagged for editor.
Corroboration is a promotion, not a filter. A single-source T2 story still publishes as "Reported" (leaders want early signal) — but the status ladder and the visual treatment make the confidence unmistakable, and the item auto-upgrades to "Confirmed" the moment a second independent source lands, with the change logged.

06 / Output Formats for Every Cadence

Templates with word budgets — and a real worked item

Five cadences, five templates. Each has a fixed section order and a word budget (attention is the constraint). The assumption ledger threads through all of them: it is born weekly and graded in every longer cadence.

Daily log — budget ≤ 1,400 words · 6–12 items · publish 09:00 SGT

  1. Top line (60 words): the single most important thing overnight + overall market temperature.
  2. Urgent flags (if any): items that tripped intraday alerts, restated.
  3. Items (each ~90–130 words) — the 8 mandatory fields, fact/inference separated.
  4. Late adds: yesterday's missed-cutoff items, flagged.
  5. Watchlist ticker: open watchpoints carried forward, with age.

Assumption ledger here: not restated daily; new predictions made in an item are tagged #thesis and swept into the weekly ledger automatically.

Weekly synthesis — budget ≤ 2,200 words · publish Monday 06:00 SGT

  1. The week in one paragraph — direction, not recap.
  2. What strengthened / what weakened — themes gaining or losing intensity.
  3. Emerging themes & promotions — signals promoted this week (§ theme registry).
  4. Path dependency — which earlier events made this week's likely.
  5. Competitive moves — by actor, mapped to portfolio.
  6. Assumption ledger — new theses recorded + prior theses graded (right/wrong/why).
  7. Watch next — 3–5 concrete watchpoints with owners.

Monthly narrative — budget ≤ 3,000 words · 1st business day, prior-month close

  1. Narrative arc — the month as a story with a thesis sentence.
  2. Theme trajectories — river deltas; which themes crossed promotion thresholds.
  3. Competitive landscape shift — net position change per competitor.
  4. Portfolio implications — per major offering (Gemini, Vertex, Agentspace, infra, security, data).
  5. Regulatory & buying-behavior signals.
  6. Ledger scorecard — month's calibration + Brier trend.
  7. Strategic implications & watch-next.

Quarterly strategy review — budget ≤ 4,500 words · QBR-aligned, SGT quarter close

  1. Strategic arc of the quarter + 3 defining moves.
  2. Durable trends — themes that graduated from emerging → durable, with evidence chain.
  3. Competitor deep-dives — each priority competitor's quarter, net threat/opportunity delta.
  4. Portfolio scorecard — where Google Cloud gained/lost narrative ground.
  5. Assumption ledger review — full quarter calibration, notable misses dissected.
  6. Scenario watchpoints for next quarter (leadership-owned).

Yearly arc — budget ≤ 7,000 words · fiscal & calendar variants

  1. The year's thesis — one sentence, defended.
  2. Strategic arcs — 4–6 multi-quarter storylines with their path-dependency DAGs.
  3. Structural shifts — what changed permanently in the market.
  4. Competitive repositioning — start-of-year vs end-of-year map.
  5. Ledger annual report — hit rate, calibration, biggest right/wrong calls.
  6. Forward theses — predictions to grade next year.

07 / Double-Click Drilldown Experience

The item is the summary; the drilldown is the analyst

The daily item is precomputed and static (instant). Drilldown is where deeper, on-demand retrieval and reasoning fire — so we pay for depth only when a leader actually asks for it.

Interaction model

  • Click/expand reveals three panels: fact pattern & timeline, offering linkage, and the verdict.
  • Two tiers: a cached deep-dive (composed at publish for every item, shown instantly) and an ask-more action that triggers live retrieval + a fresh Gemini Pro reasoning pass.
  • Every primary source is one click away; the entity graph lets you pivot to "all items involving this actor / offering."

What fires on "ask more"

  1. Vector Search over the corpus for the 10 most related prior events + the theme(s) this belongs to.
  2. Entity-graph expansion (actor's recent moves, affected offerings' recent mentions).
  3. Assumption-ledger lookup: does this confirm/refute an open thesis?
  4. Gemini Pro deep-dive prompt (§11) composes an updated fact pattern + verdict with confidence.

Verdict logic — Opportunity / Risk / Urgent / No-action

VerdictDecision ruleRationale & confidence
UrgentTime sensitivity ≥8/10 AND (competitor-priority move OR live-deal exposure). A closing decision window is the defining trait.Triggers intraday alert; 1-paragraph rationale + confidence; names the control action & owner.
RiskNegative delta to a Google Cloud offering/narrative, blast radius ≥6, but window > days.Routed to owning PM/PMM; watchpoint opened with review date.
OpportunityPositive delta OR a competitor stumble that Google Cloud can exploit; ecosystem/customer opening.Action addressed to GTM/field with a concrete play.

Latency expectations. Cached deep-dive: <150 ms (static). "Ask more" live pass: target < 6 s p50, < 12 s p95 (retrieval + single Gemini Pro call, streamed). Verdicts can change over time — the item stores a verdict history, so "Urgent → Risk → No-action" as a story cools is visible and auditable.

09 / Storage & Memory Model

Immutable facts, revisable analysis, accountable memory

The core design rule: facts are immutable and versioned; analysis is re-runnable. When new facts emerge about a past event, we never rewrite history — we append a new fact version and re-derive the analysis, keeping the full lineage. Everything below lives in BigQuery except embeddings (Vertex Vector Search) and raw payloads (GCS).

raw_article immutable

article_id, source_id, source_tier, license_tier, url, fetched_at, published_at, raw_html_gcs_uri, title, body_hash, lang, ingest_run_id

Append-only. The evidentiary record.

canonical_event versioned

event_id, version, first_seen_at, headline, fact_summary, status(confirmed|reported|rumor|disputed), member_article_ids[], primary_source_id, relevance_score, superseded_by

New facts → new version; old versions retained.

event_analysis re-runnable

analysis_id, event_id, event_version, why_it_matters, impact_gcp, affected_offerings[], competitive_implications, verdict, confidence, recommended_actions[], model_version, generated_at

Multiple analyses per event over time = verdict history.

entity_graph

entity_id, type(actor|offering|person|product|regulator), name, aliases[] · edges: (src_entity, rel, dst_entity, event_id, weight, ts)

Powers "all moves by actor X on offering Y."

theme_registry

theme_id, label, state(signal|emerging|durable|fading), created_at, promoted_at[], intensity_series[], evidence_event_ids[], impact_vectors[], portfolio_areas[]

Promotion transitions are logged with evidence (§ theme rules).

assumption_ledger

thesis_id, period_made, statement, prob(0-1), horizon, linked_theme, linked_events[], resolution(pending|right|wrong|partial), resolved_period, brier, rationale_at_grade

The accountability spine (§ eval calibration).

embeddings_index

Vertex Vector Search: article & event vectors for dedupe + RAG. Keyed to event_id/article_id; ANN with metadata filters (date, portfolio_area).

aggregation_snapshot immutable

snapshot_id, cadence(daily|weekly|monthly|quarterly|yearly), period_key, body_md, item_ids[], theme_ids[], ledger_ids[], generated_at, model_version

Every published output is frozen for audit & diffing.

Re-analysis when facts change

  1. New corroborating/contradicting article attaches to an existing canonical_event → status may change (e.g., Reported → Confirmed, or → Disputed).
  2. A new canonical_event.version is written; the old version is preserved with superseded_by.
  3. The analyzer re-runs, producing a new event_analysis row — the item's verdict can move (Urgent → Risk) and the change is surfaced, not hidden.
  4. If the event backed an open thesis, the assumption_ledger resolution is revisited at the next grading period.
Trade-off: full versioning costs storage and query complexity vs. simple overwrite. We pay it — an intelligence product that silently rewrites its own past is untrustworthy. Immutability is the feature.

Degraded mode (never publish late)

If any stage misses its window, the pipeline publishes on time at 09:00 SGT with a completeness banner ("Analysis for 3 items pending — updating by 09:30") rather than slipping the deadline. Partial > late. Missing analyses backfill and the snapshot re-freezes with a visible "updated" stamp.

Late news & off-cutoff

Items arriving after 00:00 SGT cutoff appear next day flagged "late add". Exception: anything scoring Urgent triggers the urgent_sweep intraday alert immediately instead of waiting. This keeps the daily deadline clean without missing genuinely time-critical news.

Weekend & holidays

Daily runs every day including weekends (news doesn't stop). On light days the log auto-shortens with a "quiet cycle" note. On SG/US public holidays the ingest weighting shifts (fewer T1 corporate feeds, more T4) and a holiday flag sets reader expectations. Aggregations remain anchored to the SGT calendar regardless.

Retry & failure handling

Cloud Workflows orchestrates with per-stage ret/exponential backoff (max 3), a dead-letter Pub/Sub topic, and idempotent runs keyed by ingest_run_id. A stage that exhausts retries triggers degraded-mode publish + a PagerDuty/Chat alert to the on-call. All runs emit structured logs to Cloud Logging + a run-status row in BQ.

Trade-off: Cloud Run Jobs + Workflows (chosen) vs. a single long-running service or Composer/Airflow. Jobs+Workflows give us cheap, serverless, per-stage isolation and native retries without a cluster to babysit; Airflow would add operational weight the cadence doesn't justify at this scale.

12 / Evaluation Criteria

If we can't measure "so-what," we're just a feed

MERIDIAN is evaluated on four axes: did it pick the right news (relevance), did it tell the truth (citation integrity), did it help (so-what quality), and was it right over time (calibration). A weekly eval dashboard makes all four visible.

Relevance precision / recall

Against a rolling human-labeled golden set (editors label ~40 candidates/day include/exclude). Targets: precision ≥ 0.90 (protect attention), recall ≥ 0.75 at the daily layer (misses caught in weekly). The borderline queue feeds new labels continuously.

Citation integrity & hallucination

Automated check: every sentence in a fact block must resolve to a source span (entailment check by a judge model + URL liveness). Zero-tolerance gate: an item with an unsupported factual claim is blocked from publish and routed to the editor. Target hallucination rate on facts: < 0.5%, audited weekly on a sample.

"So-what" quality rubric

Leadership raters score a weekly sample 1–5 on: actionability, portfolio-mapping accuracy, competitive insight, and non-obviousness. Target mean ≥ 4.2. Low scorers are error-analyzed; the rubric is the north star, not model perplexity.

Assumption-ledger calibration

Brier score on all resolved theses (lower = better; target < 0.18) + a reliability curve (are "70%" calls right ~70% of the time?). This is the honesty metric — it catches over-confidence the "so-what" score can't.

13 / Security, Access Control & Governance

Public-source intelligence, internal-grade controls

MERIDIAN reasons over public and licensed external content only — it is deliberately walled off from confidential internal data (deal data, roadmaps, customer PII). That separation is the single most important governance decision: it keeps the system shareable, auditable, and low-risk.

IAM & audiences

  • Least-privilege service accounts per pipeline stage; no shared god-account.
  • Reader access via Google Groups mapped to personas/regions; IAP in front of the web app.
  • Editor/override role is a distinct group with audit-logged actions.
  • LLM calls use a dedicated Vertex SA scoped to the project's models only.

Data handling for licensed content

  • License tier stored per source; full text of licensed content is never republished — store abstract/metadata + link.
  • Retention policy per source class; right-to-be-forgotten honored via article_id purge (analysis lineage preserved without the raw text).
  • No customer content flows in; prompts are templated and logged for review.

VPC-SC / CMEK posture

  • VPC Service Controls perimeter around BigQuery, GCS, Vertex — egress limited to the approved ingestion path.
  • CMEK on GCS + BigQuery + Vector Search for key control.
  • Vertex calls stay in-region (data residency); JAPAC-region option for regional deployments.

Audit logging & editorial governance

  • Cloud Audit Logs on all data + admin access; every published snapshot is immutable + diffable.
  • Editorial override: named editors can annotate, downgrade a verdict, or pull an item — every action is attributed, timestamped, and shown as an "editor note," never a silent edit.
  • A model-change log ties every output to its model_version + prompt version for reproducibility.
Separation of concerns is the governance keystone. Because MERIDIAN never touches confidential internal systems, it can be broadly shared across GTM/product/regional leadership without a data-loss review each time — and any future internal-GTM integration (H3) crosses a deliberate, reviewed boundary rather than being baked in.

15 / Future Roadmap

Three horizons, each earning the right to the next

Horizons are gated by prerequisites, not calendar. H1 completes the intelligence product; H2 makes it conversational and personal; H3 makes it predictive and connected.

H1 Full cadence & visibility

Ships: monthly/quarterly/yearly synthesis; full visualization suite (theme river, path-dependency DAG, zoomable timeline); automated theme-promotion rules; assumption-ledger with Brier calibration dashboard; live "ask-more" drilldown; source expansion to ~120.

Prereqs: ≥ 3 months of corpus for meaningful themes; stable taxonomy; MVP precision bar met.

H2 Conversational & personal

Ships: Q&A over the corpus (RAG chat: "what changed for Agentspace this quarter?"); alerting rules per user; personalization by persona/region (saved lenses, digest cadence); Chat/Slack + Workspace surfaces; multi-language regional editions.

Prereqs: clean entity graph + embeddings at scale; eval harness for answer faithfulness; access-control maturity.

H3 Predictive & connected

Ships: predictive signals (lead indicators from theme velocity + ledger calibration); scenario modeling ("if AWS cuts agent pricing 40%, likely knock-ons"); governed integration with internal GTM systems (CRM/deal signals) behind the data boundary.

Prereqs: ≥ 12 months calibrated ledger (trust the forecasts); security review for the internal-data boundary crossing; exec sponsorship.

The through-line: every horizon compounds the memory. H1 builds the corpus and calibration; H2 makes that memory queryable and personal; H3 turns a well-calibrated memory into foresight. You cannot skip to H3 — predictive value is earned by a track record the assumption ledger has already proven.
