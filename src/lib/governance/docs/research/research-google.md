## Executive summary — Google's governance philosophy in three paragraphs

**Layered, principle-anchored, increasingly agent-first.** Google's governance story starts with published frameworks rather than product features: the **AI Principles** (rewritten February 2025 around three pillars — Bold Innovation; Responsible Development and Deployment; Collaborative Progress), the **Frontier Safety Framework v3** (September 2025) governing catastrophic-risk capabilities in frontier models, and the **Secure AI Framework (SAIF)**, extended in October 2025 to **SAIF 2.0** with an agent risk map and three agent security principles: agents must have well-defined human controllers, carefully limited powers, and observable actions/planning. Google externalizes this work through the **Coalition for Secure AI (CoSAI)** — to which it donated SAIF's risk-map data — and through open protocol donations (Agent2Agent to the Linux Foundation). The message to enterprises: governance is inherited from Google's own internal practice, then made configurable in the cloud.

**"Shared fate," not just shared responsibility.** Google Cloud's stated posture is that it succeeds or fails with the customer: secure-by-default infrastructure, contractual commitments (the AI/ML Privacy Commitment — customer data is never used to train Google models without permission), generative AI indemnification, and opinionated blueprints, while the customer retains responsibility for use-case risk, data classification, prompt/response retention decisions, and regulatory obligations as an AI "deployer." Concretely, the platform ships governance as configurable primitives at every layer: org policies that allowlist models, Model Armor floors that set an organization-wide minimum prompt/response screening posture, VPC Service Controls and CMEK for the data perimeter, and always-on Admin Activity audit logs — with the sharp edges (Data Access logs, prompt logging, zero-data-retention caching settings) left to explicit customer choice.

**2025–2026 pivot: from governing models to governing agents.** The April 2026 platform consolidation makes agents the governed unit: every agent gets a cryptographic, SPIFFE-formatted **Agent Identity** mapped to IAM; an **Agent Registry** enumerates and enables/disables the fleet; an **Agent Gateway** is the policy enforcement point for tool/MCP calls with Model Armor inline; **Agent Sandbox** (gVisor) isolates code execution; and Security Command Center's **AI Protection** (AI-SPM) extends discovery, virtual red teaming, and threat detection to AI assets and agents. This is the strongest differentiation story for sellers — and also the newest surface area, so status flags (GA vs. Preview, April-2026-fresh) matter for credibility.

## How it fits together — four reference architectures

**A. Governed employee AI (Workspace + Gemini Enterprise).** An enterprise turns on Gemini in Workspace by OU with the AI control center, keeping the "AI data retrieval" toggle off for sensitive populations. Workspace DLP applies IRM to crown-jewel Drive files, which Gemini then will not retrieve; context-aware access restricts the Gemini app and NotebookLM to compliant managed devices. Chrome Enterprise Premium blocks paste/upload of labeled data into unsanctioned AI sites — converting shadow-AI demand into use of the sanctioned surface. The Gemini Enterprise app becomes the governed agent storefront: admins allowlist agents in the registry, and every user action lands in Cloud Logging usage audit logs. Compliance posture inherits FedRAMP High (US public sector) or the Workspace BAA (healthcare) where applicable.

**B. Governed custom genAI application (Agent Platform + Model Armor + SDP + VPC-SC).** A customer-facing app calls Gemini (or Claude) through the Gemini Enterprise Agent Platform inside a VPC Service Controls perimeter, with CMEK on stored artifacts and regional endpoints for residency. An org policy (`vertexai.allowedGenAIModels`) pins the approved model list; teams pin model versions and plan migrations against published retirement dates. Model Armor floor settings guarantee minimum screening org-wide; the app's template adds advanced Sensitive Data Protection de-identification so PII is redacted in both directions and in logs. Data Access audit logs are enabled; opt-in prompt/response logging (post-redaction) feeds review workflows. Pre-launch, the Gen AI evaluation service (LLM-as-judge plus grounding metrics) gates releases; Provisioned Throughput reserves capacity for the production tier while DSQ absorbs dev/test.

**C. Governed agent fleet (ADK + Agent Runtime + Agent Gateway + SCC).** Agents are built in ADK (auto-instrumented with OTel GenAI conventions), evaluated with agent evals and simulation, then deployed to Agent Runtime with Sessions and Memory Bank (CMEK-protected). Each agent receives a SPIFFE-formatted Agent Identity bound to IAM, so least-privilege applies to the agent itself, not just its human invoker. All tool and MCP calls traverse the Agent Gateway, where Model Armor screens payloads and policies constrain which tools each agent may touch; the Agent Registry is the fleet inventory and kill-switch. Untrusted code execution is pushed into Agent Sandbox (gVisor) — on GKE for self-managed fleets. Security Command Center's AI Protection supplies the AI/agent inventory, virtual red teaming over the environment's digital twin, the Agent Security dashboard, and anomaly/threat detections; Audit Manager collects evidence against ISO 42001/NIST AI RMF. This is SAIF 2.0's three agent principles rendered as products: human controllers (IAM + registry), limited powers (gateway + identity), observable actions (traces + audit logs).

**D. AI gateway for a heterogeneous model estate (Apigee-fronted).** Where the enterprise already consumes OpenAI, Anthropic, and self-hosted models alongside Google's, Apigee becomes the single AI front door: per-consumer token quotas, semantic caching for cost, model routing/failover, API analytics for chargeback — and Model Armor invoked as a policy so injection/leak screening is uniform across providers. The Application Load Balancer chains Cloud Armor (WAF/DDoS) and Service Extensions so even non-Apigee AI traffic (agents, MCP servers) gets Model Armor screening in the network path. SCC AI Protection watches posture across it all. This is the pattern to lead with for customers who say "we're multi-vendor on models" — the governance layer is deliberately model- and cloud-agnostic.

## Honest gaps & shared-responsibility items (credibility section)

1. **GenAI drift monitoring doesn't exist as a turnkey product.** Model Monitoring v2 covers predictive/tabular drift; for LLMs the customer must assemble continuous evaluation (online evals, autoraters) + dashboards. Say this plainly.
2. **Model allowlisting has scope limits.** The org policy governs Model Garden models only — not models imported into Model Registry or arbitrary self-hosted weights on GKE/GCE; 500-value cap; custom policies enumerate models individually.
3. **Gemini safety filters don't apply to partner models.** Claude/Llama bring their own behavior; the cross-model control is Model Armor — position it that way, and note Model Armor adds latency and (for advanced SDP) cost.
4. **Audit logs never contain prompts.** Content-level audit requires deliberately enabling request-response logging; the customer then owns retention, access, and PII handling of those logs (mitigate with SDP redaction).
5. **Caching is on by default; ZDR is a configuration, not a default.** 24h input caching must be disabled per project for zero retention; verify abuse-monitoring terms per service during contracting.
6. **Residency lags the frontier.** Newest Gemini versions frequently launch global-endpoint-only; EU/regional ML-processing for the latest model can trail by months. Never promise residency without checking the per-model matrix.
7. **Aggressive model lifecycle.** Retirement windows (~6 months post-successor; access blocked a month before retirement) force migrations; version pinning is temporary. Customers need a model-migration runbook — this is a governance cost of the platform.
8. **Open models exit the control plane.** Once Gemma 4 (Apache 2.0 — no usage restrictions) or other weights are downloaded, platform guardrails, filters, and logging no longer apply; governance is entirely the customer's (license changed from the restricted Gemma ToU precisely to enable this freedom).
9. **Grounding reduces, doesn't eliminate, hallucination** — and Grounding with Google Search has cost and data-egress-to-Search considerations; citations still need human-in-the-loop for high-stakes output.
10. **EU AI Act conformity is the customer's.** Google supplies certifications (ISO 42001), logging, Audit Manager evidence and commitments — but risk classification, FRIA, human oversight design, and deployer/provider obligations belong to the enterprise.
11. **The agent governance stack is very new.** Agent Identity, Registry, Gateway, Anomaly/Threat Detection, Sandbox all landed April 2026; expect Preview labels, sparse regional coverage, and evolving APIs — check status per component before committing in proposals.
12. **Principles optics.** The Feb 2025 AI Principles rewrite removed the explicit weapons/surveillance prohibitions; some customers (and public-sector stakeholders) will raise it — prepare a considered answer rather than being surprised.
13. **Naming churn is itself a governance risk for customers** (Vertex AI → Gemini Enterprise Agent Platform; Agentspace → Gemini Enterprise; Dataplex Universal Catalog → Knowledge Catalog; Vertex AI Search → Agent Search — all within ~8 months). Docs, IAM role names, and API endpoints remain stable, but internal policies/runbooks referencing old names need an update pass — a genuine consulting opportunity.
